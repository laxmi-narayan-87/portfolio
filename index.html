05 / Quality & security

Trust is built into the workflow.

Quality evidence should show what was tested, under which conditions, what failed, and what changed — not just that a tool was used.

Quality evidence

  • Test cases grouped by feature and user journey
  • Boundary, invalid-input, empty-state, and permission cases
  • Reproducible bug reports with expected vs actual behaviour
  • Automated test output and environment notes
  • Clear separation between implemented, tested, and planned work

Security foundation

  • No secrets, tokens, private keys, or personal identifiers in source
  • Least-privilege access; server-only secrets never shipped to browsers
  • Validate untrusted inputs and avoid unsafe DOM injection
  • Use HTTPS and restrictive security headers at the hosting layer
  • Review dependencies and run checks before deployment

This static portfolio does not need a database, login, tracking scripts, or a contact form. Keeping the attack surface small is intentional.
